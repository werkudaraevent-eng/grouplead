# LeadEngine design rules

The CRM follows Material Design 3 as rules and logic (structure, spacing,
hierarchy, colour, how a control behaves), never as a visual copy, with
global platforms (HubSpot, Salesforce, Linear, Notion) as references for
patterns Material leaves open. The sibling app records the same discipline
in `apps/sales-mission/DESIGN.md`; the two apps share a session, a colour
system and a set of shell behaviours, and should read as one product.

| Area | Rule (and where it comes from) | Where it lives |
|---|---|---|
| Tokens, not hex | Every colour is a token from `app/globals.css` (M3 tonal surfaces: `--background` surface, `--muted` surface-container-low, `--card` surface-container-lowest, `--sidebar` the navigation panel only, which the person can switch to dark independently of the content, so nothing outside the drawer and its menus may use it, `--border` outline-variant, `--primary`, `--secondary`, `--accent`, `--warning`, `--success`). A raw hex or Tailwind palette colour in a component is a bug, because it cannot follow a theme or a rebrand | `components/ui/*`, `components/shared/*` |
| List pages | Page header with the one primary action; then one toolbar exactly one row tall: an M3 search bar (pill, leading icon, trailing clear, debounced), filter chips in a rail that scrolls sideways rather than wrapping, and secondary actions as 40dp round icon buttons with tooltips. Saved views appear as choice chips only once a view exists; the first is saved from the toolbar. The list never moves because the toolbar grew (M3 top app bar, filter chips, icon buttons; Linear, Attio) | `ListToolbar`, `SearchField`, `FilterBuilder layout="rail"`, `ToolbarIconButton`, `ColumnsMenu`, `SaveViewButton`, `SavedViewsBar` |
| Data table | Header on surface-container-low, 52dp rows, one hairline between rows, hover as a tonal wash, selection as a primary tint, frozen leading columns with one edge shadow, the row's actions as a trailing round icon button that appears on hover or focus, a fixed-height footer with the range on the left and paging on the right (M3 data table, list item, pagination) | `components/ui/table.tsx`, `components/shared/list-table.tsx`, `ListFooter`, `InitialsAvatar`, `NeedsDetailsBadge` |
| Chips | Filter chips are 32dp pills: tonal (`bg-primary/12 text-primary`, leading check) when they narrow the list, outlined otherwise; choice chips (roles, saved views) the same shape with one selected (M3 chips) | `filter-builder.tsx`, `saved-views-bar.tsx`, `settings/permissions/page.tsx` |
| A field reading is a badge, signed | A judgement sent from the field (a contact's DISC communication style) sits in Contact Information as a small tonal badge (`bg-primary/10 text-primary`, the filter-chip tint) with its meaning beside it, the rep's note under it in their own words, and who assessed it and when in the meta size; it is one person's impression on one day, so it is never rendered as a status or a fact, and it is replaced by a newer reading rather than merged (Crystal Knows and Humantic AI beside a HubSpot or Salesforce contact; M3 assist chip, supporting text) | `DiscRow` / `readDisc` in `features/contacts/components/contact-detail-page.tsx`, written by `POST /api/v1/contacts` into `custom_fields.disc` |
| The AI bill is shown where the connection is set, in tokens, as a pace | Every call to the proxy from either app writes one line to a shared log (app, feature, model, tokens in and out, ok), and Settings → AI shows a Usage card under the connection: the last 7 and 30 days as calls and tokens, then what a week and a month cost at the last week's pace, then the split per feature and per model, because the person paying wants the monthly token figure before the invoice, not after (OpenAI's and Anthropic's usage pages, Vercel AI usage, Salesforce's Einstein request consumption all sit beside the credentials). Tokens, never currency: the price is the proxy's and would go stale here. A log younger than a week projects from the days it covers, an empty log says so instead of showing zeros, and failed calls are counted but carry no tokens. One plain table set, not a chart | `public.ai_usage` (migration `20260921090000_ai_usage.sql`, service role only), `recordAiUsage` / `summarizeUsage` / `readAiUsage` in `lib/ai/ai-usage.ts` (written by `askAI`, `analyzeDashboard`, the Save probe), `AiUsageCard` in `features/settings/components/ai-usage-card.tsx`; Sales Activity mirrors it |
| Integration settings: written keys, tested connections, chosen from what the endpoint reports | A connection to an outside service is one page in two cards: the connection (endpoint, key), then what it offers (models). The key field is empty on every visit and names the stored key only by its last four characters, because a secret is written and never read back (HubSpot integrations, Zapier connections, Vercel environment variables); "Test connection" makes one real request, reports the outcome as a sentence with a check or a cross, and fills the model pickers from the answer, so a person chooses among models the endpoint actually serves (Metabase database test, Grafana data sources); a picker falls back to a text field when nothing is listed, and a stored value the endpoint no longer lists stays selectable. Saving tests again so the stored status describes what was stored, and also asks each chosen model for one word, because a model can be listed and still not answer (a reasoning model given a small token budget answers with nothing); that failure belongs on the settings page with the model's stop reason in a sentence, never as a code on the dashboard. The same connection is shared with Sales Activity and shown identically there | `AiSettingsForm` in `features/settings/components/ai-settings-form.tsx` under Settings → AI, `app/actions/ai-settings-actions.ts`, `lib/ai/ai-proxy.ts`, `lib/ai/ai-settings.ts` (Vault-backed key via `fn_ai_store_key` / `fn_ai_read_key`, service role only); `lib/ai-client.ts` resolves the stored connection with the AI_* env as fallback |
| Who may see and change what | Role & Izin: modul × Lihat/Buat/Ubah/Hapus with a reach (Cakupan) under Lihat and Ubah; role chips on top, one pane, the reading guide folded | `app/(app)/settings/permissions/page.tsx` |
| Drawer rail vs account menu | The drawer holds destinations and one Administration group for Settings; the profile, the changelog, the panel toggle and sign-out live behind the account menu at the foot of the drawer, on the panel's own tokens, with no focus ring left behind on close (M3 navigation drawer; Slack, Notion, Linear). Same pattern as Sales Activity | `components/layout/sidebar.tsx` `adminNav` and the `DropdownMenu` on the profile block |
| Switching apps | A transit screen on leaving and a loader on arrival, both on the shared preference cookies, so the sidebar arrives at the width the person left it at | `components/layout/{app-transit,app-switcher,top-loader}.tsx`, `lib/preference-cookie.ts` |

Out of scope for now, recorded so it is not mistaken for a rule: the list
pages still fetch a whole table and filter, sort and page in the browser;
server-side paging is a separate change.
